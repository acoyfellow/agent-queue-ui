# Pre-build receipt schema review

These five examples test whether one honest receipt vocabulary can represent the hard cases before software exists. They are schema exemplars, not evidence that the UI claim is proven.

| Case | Outcome | Observed | Projected | Realized |
| --- | --- | --- | --- | --- |
| Fix with mechanical gate | planned | A queue item must have exactly one visible state and stable ID | A deterministic interaction test can reject lost or duplicated turns | Not yet |
| Verified disproved | exemplar | A user study may show the side rail does not reveal queue position within five seconds | A disproved receipt would retire this layout while preserving the chat substrate | Not yet |
| Surface-reducing deletion | planned | The experiment needs no router, server, database, auth, or model SDK | Keeping the first iteration frontend-only isolates the queue question | Not yet |
| Reusable hammer | planned | Messages and queue entries can share stable participant and turn identities | Later queue layouts can reuse one simulation model | Not yet |
| Negative result | exemplar | A visually polished queue may still fail when attention is split from the transcript | Record comprehension failure rather than treating completed UI as success | Not yet |

The schema keeps observation, projection, and realized reuse separate, and can represent a negative result without laundering it into progress.
